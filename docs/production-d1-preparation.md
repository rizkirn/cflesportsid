# Production D1 preparation

Production access is not implied by plan preparation. `scripts/phase2c/production-preflight.mjs` adds a focused production-only read client alongside existing Phase 2B/2C infrastructure. It reuses the pinned schema comparator, source checksums, private approval reader, environment rejection and media key contract. Staging transports, UAT validators and runtime mode guards are unchanged. There is no mutation transport or deployment configuration in this preparation.

The proposed target is account `bf6ed4ccd73133871881b47ea58dae3d`, Worker `cflesportsid`, D1 `cflesportsid` / `efded3c4-1cf9-46a9-823e-d0f2d17c683a`, hostname `cflesports.com`. These are local target expectations, not current live verification. A mismatch stops execution. No default Wrangler config is consulted. An unexpected additional D1 binding, staging bucket, ambiguous deployment, routing conflict or unreviewed service binding stops verification rather than silently relaxing isolation.

The plan pins implementation/fixture/migration hashes, fixed queries, operation, target, nonce, limits and expiration. Explicit approval uses the existing private Phase 2B approval record shape with operation `production-read-only-preflight` and the exact production target and plan digest. Approval lifetime is at most 30 minutes, and cannot exceed the plan's 24-hour lifetime. The approved run exclusively claims its plan before the first request; a repeated attempt is rejected, including after failure. The caller must obtain credentials only after human approval and must never print them. The module does not load or refresh credentials.

Bounds: 15 minutes, at most 160 account API requests, at most 256 public photo HEAD requests, 30 seconds per request, no redirects or retries. GET endpoints inspect the exact account/database/Worker, versions, deployed routing, script settings and discovered production R2 bucket metadata. Only exact allowlisted SELECT/PRAGMA statements use D1's POST query endpoint; every result must report zero rows written. No export, bookmark, import, configuration, deployment or restoration endpoint is permitted. Public HEAD requests are restricted to valid current D1 photo keys on `https://cflesports.com/media/`; they receive no Cloudflare authorization header. No public page GETs or UAT tests are included.

The run checks schema/ledger 0010 or 0011 without changing either; determines whether 0011 is pending; checks foreign keys, schema objects, columns, indexes and inbound roster references; compares the 168 historical memberships independently of saved positions; captures exact saved-position hashes; checks historical boundaries and the known current master identity; determines whether the exact pinned historical mapping is absent or already present; rejects conflicts. Additional official roster records outside S1/S2 are not erased or seeded. Repeated reads detect changes to schema, ledger, identities, rosters, photos, active bindings and routing. This is not an atomic snapshot: production writers must later be paused for the approved backup/cutover window.

Photo preservation: capture all non-null `players.photo_asset_key` rows (over 256 stops this bounded plan), validate UID/key correspondence, hash the metadata privately, and check media HEAD availability. Direct R2 object existence remains UNVERIFIED because HTTP caching can satisfy HEAD without reaching R2. Direct object HEAD needs a separately reviewed read mechanism; do not invent S3 credentials or deploy a helper Worker. Bucket identity, media availability and object existence are separate evidence. D1 export/recovery does not back up R2 bytes, and export/restore permissions are not proven without exercising the separately approved operations. Secrets are represented by their available binding metadata; their stored values are not independently read or verified.

Migration and backfill decisions are made from the production ledger/schema and exact existing identity rows. Never copy staging SQL, a staging database, JSON seeds or staging R2 objects to production. Migration 0011 and the pinned identity artifact do not update player photo metadata. Freeze uploads during later backup/cutover; verify production photo-reference hashes before/after each change and verify each newly uploaded object's original media path. Restoration can discard post-backup references even when R2 objects survive.

Minimal sitemap follow-up: reuse `publicSitemapPaths(snapshot)` and the existing XML projection from `/local-verification/sitemap.xml` for the canonical sitemap child endpoint, preserve `/sitemap-index.xml` and its current child URL(s), merge existing static public routes, and preserve robots/canonical URLs. Remove build-time tournament entity enumeration from JSON in `astro.config.mjs`; ensure generated static sitemap files cannot shadow the dynamic endpoint. The new endpoint must be runtime-rendered, include official D1-only entities and historical profiles, exclude admin/test-only entities and fail explicitly on D1 errors. Discover the actual live sitemap URLs during separately approved production verification before sealing this change. No sitemap or reader behavior is changed now.

Then obtain separate approvals for backup, local recovery rehearsal, migration if needed, backfill if needed, deployment, reader activation and smoke tests. Retain a verified hybrid Worker compatible with 0011 and production photo delivery. Any rollback or restoration requires its own approval. No automatic restoration is allowed.
